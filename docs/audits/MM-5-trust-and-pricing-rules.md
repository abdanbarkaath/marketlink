# MM-5 — Trust and pricing rules

[MM-5](https://marketlinksetup.atlassian.net/browse/MM-5) · Source baseline `734ed16` · [Product and audit guidance](../product/intent-and-audit-priorities.md)

The buyer should be able to compare service fit, understand what a provider has shared about price, and identify the source of reviews and other proof before making contact. This is a source audit. **VERIFIED** describes code behavior, **PARTIAL** describes a verified mechanism with unknown provenance or policy, and **UNVERIFIED** describes runtime evidence still needed. The expected benefits below were not measured.

## Context from prior audits

- [MM-2](MM-2-public-copy-and-entry-points.md) keeps the real directory, disclosed homepage examples, guest inquiry, and data-backed signals. The public routes are `/experts` and `/experts/{slug}`; `/providers` and `/providers/{slug}` are compatibility redirects.
- [MM-3](MM-3-api-contract-audit.md) documents API aliases, public projection and validation gaps. Changes to displayed trust or price need an explicit decision about API behavior and legacy consumers.
- [MM-4](MM-4-service-token-mapping.md) establishes service-token compatibility. A listing’s service fit comes from its recorded services and relevant work. A “Reviews & Reputation” service tag describes an offering and supplies no review evidence for the provider.
- [MM-119](MM-119-agency-onboarding-audit.md) and the [owner-flow audit](../superpowers/audits/2026-04-29-mm15-owner-flow-contract-audit.md) document optional pricing and proof and the owner edit boundary. MM-120 subsequently added publication confirmation for nonempty project, client, and media updates. [Current write path](../../marketlink-backend/src/routes/providers.ts#L1462)
- [Design contract](../../DESIGN.md#L52) calls for actual provider-entered price guidance and a quote for ongoing support. [Browse implementation](../product/browse-c-implementation.md) describes the live comparison surfaces.

## Acceptance tests for an approved follow-up

1. **T1 — Verification.** Use true/false fixtures and an admin versus provider session. A provider cannot self-verify. Check the approved label and scope, filter behavior, map/card/detail parity, and missing flags. If a label is shown, its meaning must be available as text and operable by keyboard and touch.
2. **T2 — Aggregate rating.** Cover default zero, positive score with unknown count, out-of-range values, empty eligible reviews, and a valid score/count from the same eligible set. A default score must not be interpreted as a review. Keep list and detail consistent with the approved policy.
3. **T3 — Reviews.** Use approved historical, null, future-dated and unapproved fixtures. Check detail API aliases and signed-out UI for matching eligible rows. Confirm expected public fields and deny unsupported review claims; verify empty state and approved legacy backfill plan.
4. **T4 — Price amounts.** Exercise null, zero, negative legacy data, min-only, max-only, equal, valid range, inverted range and project-only records. Check list, compare, detail and a save/reload. Clear a field and ensure other prices persist.
5. **T5 — Currency and estimates.** Test USD, a supported alternate currency, ambiguous symbols and rejected/legacy invalid codes under the chosen policy. Check per-hour units, quote-only, advertising costs and nonbinding guidance. Use accessible text and check wrapping at 320px and 390px.
6. **T6 — Proof and privacy.** Test no work, a permitted redacted project, identifiable client attribution, legacy proof review and credentials with/without issuer links. Verify no publication confirmation metadata or hidden location leaks in public responses. Confirm keyboard access, meaningful image alternatives and fixture labels.
7. **T7 — Discovery regression.** Verify direct service search, old filtered links, directory and API aliases, guest inquiry, name/date/distance sorting and pagination. Check current request matching separately before changing trust-related ranking. Profile URLs, public contact and metadata continue to identify the actual listing.

## Order and planned evidence

First decide public review eligibility and provider verification language, including what to do with legacy flags and rows. Then approve a single pricing rule and fix rating-empty and pricing inconsistencies. Revisit ranking only with its own decision and evidence. Keep public search and guest inquiry intact through each follow-up.

**PLANNED.** Ask U.S. small-business buyers to compare a few controlled profiles by service fit, identify which prices are available and their units, explain the chosen verification label, and choose a contact action. Record correct answers and completed tasks over total attempts. For qualified inquiry intent, count whether a participant chooses a provider matching a stated service need and identifies enough scope to start a conversation. For actual completion, count successful inquiries separately from profile opens and form starts. Use aggregate counts and omit contact details, client names, inquiry text and precise location from measurement. Study and instrumentation require separate approval.
