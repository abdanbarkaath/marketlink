## Current matching contract

| Entry point | VERIFIED behavior |
| --- | --- |
| `skills=area.service,…` | The Next page resolves IDs from `directoryFilters`. Each selected ID becomes a token group. `any` matches any token in the union. `all` requires at least one token from each selected group. A shared token can satisfy multiple groups. |
| `subject` or `subject` + `subcategory` | Resolves the full taxonomy token set and sends flat `service` with `match=any`. Subject takes precedence over a goal, while subcategory takes precedence over subject alone. |
| `problem=<taxonomy goal ID>` | Uses that goal’s suggested tokens with flat `match=any` when no resolved skill, subject or subcategory takes precedence. |
| `service=a,b` | Legacy/direct comma-separated API filter, also forwarded by the page when no derived mapping wins. Tokens are trimmed and lowercased. `any` uses `hasSome`. `all` uses `hasEvery`, so each token must be stored. One token uses `has`. |
| `serviceGroups=[[…],…]` | Backend query generated by the directory. The parser requires valid nested arrays and lowercase alphanumeric/hyphen tokens, with at most 64 groups, 50 tokens per group, 80 characters per token, and a 12,000-character query value. If both `service` and `serviceGroups` reach Fastify, both filters apply. |
| `q` and `name` | `q` matches business name, tagline, short description, or an exact service token after lowercasing and replacing whitespace with hyphens. It does not expand catalog aliases. `name` is a business-name substring filter. The catalog picker search searches option labels, descriptions, keywords and selected phrase aliases. |
| Legacy `/providers` | The frontend list redirects with query parameters and the detail page redirects by slug. The backend continues to register `/providers` and `/providers/:slug` aliases. List results include active records only and combine service matches with other applicable filters. |

A supplied array/string on PUT replaces services after normalization and a nonempty check. These handlers do not enforce catalog membership. The owner picker turns help selections into the union of full subcategory tokens. ## Legacy tokens, overlaps and missing mappings

- **VERIFIED — Seeded legacy tokens.** Repository expert seed arrays use `seo`, `ads`, `social`, `web`, `email`, `print`, `video`, `content`, `branding`, `reviews` among other values. All 65 distinct tokens from the seven expert seed arrays appear in the full taxonomy. These are seed values. Live records were outside the audit. [Seed arrays](../../marketlink-backend/prisma/seed.js#L18)
- **PARTIAL — Some aliases are searchable as labels yet excluded from the applied directory group.** “Facebook ads” and “Instagram ads” can find the Meta Ads option, but choosing it queries `meta-ads` only. A record storing just `facebook-ads` or `instagram-ads` can match the full taxonomy path or direct `service` filter and miss that directory choice. Similarly, `paid-search` alone can miss the Google Ads shortcut. Use explicit compatibility tests before adding token aliases to live groups. Expanding to every broad or deliverable token would also change which results appear. [Directory option search and filter tokens](../../marketlink-frontend/src/lib/directory.ts#L3)
- **PARTIAL — Ambiguous and unknown are different cases.** A shared token such as `ads` can select multiple categories without proving a specific platform offering. An area-only token such as `influencer` is recognized by the taxonomy, but public grouping requires a subcategory/deliverable match. A token absent from every taxonomy level has no picker option or taxonomy mapping. Existing fallback rendering and exact `service` filtering can still represent a custom token. The audited seed arrays had no unknown tokens. The existence or count of custom live tokens is unverified. [Grouping/fallback](../../marketlink-frontend/src/lib/marketingTaxonomy.ts#L1431) · [Backend matching](../../marketlink-backend/src/routes/providers.ts#L575) · [MM-119 scenarios](MM-119-agency-onboarding-audit.md#scenario-and-disclosure-rules)

**PARTIAL.** `discovery.ts` also defines eight broad service paths and six problem cards. The current homepage mounts `HomeMarketplace` and does not consume those card exports. Some card IDs differ from taxonomy goal IDs, for example `cant-find-business` versus `cannot-find-business` and `not-sure-what-i-need` versus `not-sure`. `getDiscoveryProblemHref` emits the card ID and a flat service list from its suggested paths. Those links can still filter using the explicit `service` value, but a card-only `problem` value with an unmatched ID cannot resolve the taxonomy goal or its label. IDs that happen to match can trigger taxonomy goal precedence over the helper's emitted service list. In particular the two launch mappings suggest different areas. Guidance should describe possible services rather than guarantee a result.
